What is Scan4Earn?

Scan4Earn (scan4earn.com) is a multi-tenant Application-provisioning platform — and at its core, a BaaS (Backend-as-a-Service). Scan4Earn never ships the surface a real consumer shops or scans on; it ships the backend and the APIs behind it. A Tenant is a reseller/agency that onboards other companies as clients and provisions an Application for each one — either an ecommerce store (inventory, products, orders) or a scan-and-earn campaign (QR coupons that pay consumers points or UPI cashback directly — no middlemen). Every Application gets its own API keys, its own branding, its own dashboard, and — this is the rule that shapes the whole product — exactly one owner login: the external business that actually runs it.

The BaaS relationship, explicitly

The moment a Tenant provisions an Application, Scan4Earn generates the full backend API surface it's entitled to — ecommerce APIs (catalog, cart, checkout, orders, addresses) or scan-and-earn APIs (scan verification, consumer auth, UPI/profile, history, cashback), or both for a HYBRID Application. The Application Owner's job — end to end — is to integrate those APIs into their own consumer-facing surface: a website for ecommerce, and/or a mobile app for scan-and-earn.

The website (or app) is entirely the Application Owner's own. Scan4Earn places zero constraint on its framework, design, or hosting — the relationship is API-only. This is what makes the value proposition real: the business never builds a catalog/inventory engine, an order state machine, payment collection & reconciliation, consumer OTP authentication, fraud-safe coupon/scan logic, or cashback payout mechanics. All of that is Scan4Earn's problem. The business only owns the look, feel, and content of its own site.

The one rule that defines this product: Orders, inventory, stock, scans, cashback, coupon burn-down — any real business-operational number — exists only inside an Application's own dashboard. Neither the Super Admin nor the Tenant Admin has a single screen that shows this data, in any form, even aggregated. Their dashboards are provisioning & billing consoles. Full stop.

Who

Roles & Access Levels

Three levels of login, plus the consumer. There is no Dealer role and no App Viewer role — an Application has exactly one owner login, and business data lives nowhere except inside that Application.

LEVEL 1Platform
Super Admin — you, the platform ownerLogs in at scan4earn.com. Creates Tenants and their subdomains · approves credit requests · records subscriptions · manages global feature flags & the template library · sees platform-wide counts (Tenants, Applications, credits sold). Never sees an order, a stock number, a scan, or a cashback amount, from any Application, ever.
▼
LEVEL 2Tenant (reseller)
Tenant Admin — e.g. Raj (Vertex Retail Partners)Logs in at the Tenant's subdomain (or custom domain). Provisions Applications for client businesses, sends the owner-invite, requests credits, sees an administrative list of its Applications: name, client, type, status, subscription tier, credits consumed. Cannot open an Application's operational dashboard — no inventory, no orders, no scans, no campaign controls. That belongs to the client alone.
▼
LEVEL 3Application (one owner)
Application Owner — e.g. Mr. Pal (Paint Coupons + Pals Paint Store), Meera (Sumukham Store + Sumukham Rewards)The external business that bought the Application from its Tenant. Sole login for that Application (or Applications, if the same business owns more than one). Full operational control: for ecommerce — products, inventory, orders, customers, coupons, API keys; for scan-and-earn — batches, codes, scan history, cashback/points ledger, redemptions. Integrates the Application's API into their own website and/or mobile app — fully their own design, framework, hosting; Scan4Earn is API-only behind it (see Consumer Identity, Checkout & Mobile Apps). Can never see a sibling business's Application, the Tenant portal, or another Tenant.
▼
LEVEL 4End user
Consumer — e.g. PriyaOne unified phone+OTP identity per Application — no separate sign-up form, ever. Scans QR codes directly (guest, or via the Application's own mobile app) → points or UPI cashback, or shops on a store powered by an ecommerce Application (checkout itself requires the same OTP step). No dealer, no intermediary. Scoped per Application — the same phone number on two different Applications is two unrelated accounts.

Access matrix — the rule of thumb

RoleScope of visibilityCan never see
Super AdminTenant count, Application count & type per Tenant, subscription/billing status, platform credit ledgerAny order, inventory, stock, scan, cashback, or coupon-burn data — anywhere on the platform
Tenant AdminIts own Tenant's Application list — name, client, type, status, owner, credits consumed, subscription tierAny order, inventory, stock, scan, or cashback data belonging to any Application it provisioned

Rule of thumb: if a screen shows an order, a stock number, a scan count, or a cashback amount, it belongs inside an Application dashboard — full stop. It is architecturally impossible for that data to reach a Super Admin or Tenant Admin screen, because those roles' APIs never touch Application-grain tables (see Data Model).

Why paths, not nested subdomains?

  • TLS: a wildcard cert *.scan4earn.com does NOT cover store.vertexretail.scan4earn.com — nested subdomains would need per-Tenant wildcard certs.
  • Simplicity: the existing subdomain handling only understands one level; paths cost nothing.
  • Consistency: the Application selector in the portal header becomes a switcher that just navigates between /apps/:slug/ paths — but the switcher only ever lists Applications the logged-in owner actually owns.

Scenarios B1 / B2 — Customer Domains (premium)

A custom domain is an optional paid alias — one row in a custom_domains table pointing a hostname at a Tenant's reseller portal or at one specific Application. Same database rows, same APIs, same portal code. Both URLs work simultaneously.

B1 — Vertex whitelabels its reseller portal (Tenant-level domain)

Raj doesn't want his clients seeing vertexretail.scan4earn.com — he maps partners.vertexretail.com. One row with application_id = NULL. This is still the administrative portal — no business data lives here regardless of which domain fronts it.

Their URLEquivalent default URL (still works!)

B2 — An Application Owner maps their own domain (the common case)

Pals Paint and Sumukham are real, separate businesses — each will almost always want its own domain on its own Application, not a path under Vertex's subdomain. One row with application_id = <that Application> maps the hostname to exactly that ONE Application. The host defines the maximum scope: the hostname serves only that Application's routes — sibling Applications and the Tenant portal are unreachable from it.

How a Request Resolves

One middleware turns ANY hostname into a Tenant + Application context. A second, independent check then confirms the authenticated user is allowed to act on that context — hostname resolution alone is never sufficient authorization.

The resolution ladder — checked in order, first match wins

1. Custom domain?SELECT … FROM custom_domains WHERE hostname = req.hostname AND status='active' → sets tenant_id (+ application_id if Application-scoped)
→
2. Our subdomain?host ends with .scan4earn.com → parse the slug (vertexretail) → look up the Tenant
→
3. Root domain?host is exactly scan4earn.com → Super Admin context
→
4. Unknown host404 — never guess

Then the identity check — the part that enforces the ownership rule

Incoming requestHost resolutionIdentity check
GET vertexretail.scan4earn.com/apps/sumukham-store/dashboardtenant=vertexretail, application=sumukham-storeCaller's JWT user_id must equal applications.owner_user_id for that Application — Raj's Tenant-Admin JWT fails this check → 403, even though the host resolved fine
POST shop.sumukham.com/api/ecommerce/v1/orderstenant=vertexretail, application=sumukham-store (app-scoped custom domain)API-key based — the key itself is minted for this Application only
GET vertexretail.scan4earn.com/tenant/dashboardtenant=vertexretail, application=nullCaller must be Vertex's Tenant Admin (Raj) — the query behind this route only ever touches Tenant-grain tables, so there is nothing operational to leak even if the check were skipped

Login & sessions on any host

1. Page loadsAngular boots, calls GET /api/tenant-branding — middleware already resolved the host
→
2. OTP loginemail → OTP; the OTP email's links are built from THIS host
→
3. JWT issuedcarries tenant_id (+ application_id ONLY for Application Owners — a Tenant Admin JWT never carries this claim at all)
→
4. Scope enforcedevery API call re-checks: scope = min(role, host) AND identity = registered owner for any Application-grain route. Wrong combination → redirect or 403, server-side, not just hidden menus

Money

Billing & Credit Hierarchy

Three independent money layers, stacked. Layer 1 and Layer 2 apply to every Application regardless of type. Layer 3 exists only for the scan-and-earn side of an Application's activity.

Layer 1 — Super Admin ⇄ Tenant (subscription plan)

Governs how many Applications a Tenant may provision — nothing more.

1. Configurable plan catalogSuper Admin manages it — e.g. Plan 1 ₹2,000/mo up to 3 Applications, Plan 2 ₹5,500/mo up to 10, Plan 3 ₹50,000/mo unlimited. Super Admin can add more plans any time, no deploy needed
→
2. Tenant picks a plan + durationtotal = plan price × months chosen. Pays via gateway checkout
→
3. Confirmed payment (webhook)activates the subscription, sets the Application ceiling
→
4. Ceiling enforcedprovisioning the next Application beyond the plan blocks with an upgrade prompt — no overage billing

Layer 2 — Tenant ⇄ Application Owner (flat per-Application subscription + single-page paywall)

Governs whether one specific Application works at all — applies uniformly to ecommerce, scan-and-earn, and hybrid.

1. Tenant sets custom termsat Application-creation time: price-per-month + duration (1/3/6/9/12 months) — different per Application, Tenant's choice
→
2. Owner accepts invite → Activate & Payfirst login shows ONE page: price × duration = total, pay button. Nothing else is reachable until paid
→
3. Confirmed payment (webhook)activates for the paid period; renewal (early or after a lapse) uses the same single page
→
4. Unpaid/expired = everything stopsowner dashboard, public storefront/API, AND the scan landing page all show the same "temporarily unavailable" / Activate & Pay response — not just the dashboard

Assumption: a Tenant's own Layer 1 plan lapsing does not cascade to suspend its already-paid Applications — each Application's uptime depends only on its own Layer 2 status. A lapsed Tenant plan only blocks provisioning new Applications.

Layer 3 — Scan-and-earn only: the credit cascade

A separate gate stacked on top of Layer 2 — an Application can be fully paid-up on its subscription and still be unable to create a coupon batch because its own credit balance is empty.

1. Super Admin sets the rateone platform-wide INR-per-credit price
→
2. Tenant buys creditspays Super Admin (rate × amount) → confirmed payment IS the approval, credits tenant_credit_balance
→
3. Tenant sets its own resale rateoptional — defaults to the platform rate
→
4. Application buys credits from its Tenantcapped at whatever the Tenant itself currently holds — a Tenant can never oversell. Payment credits application_credit_balance and debits tenant_credit_balance by the same amount, atomically
→
5. Coupon batch = auto-debitcapped at the Application's current balance, debited atomically at creation — no bypass path
Settlement is a separate system from the credit ledger: when a consumer actually scans and cashback triggers, the real UPI payout is disbursed from the Super Admin's own payment/payout account — unchanged from the platform's single central payout architecture. Credits are purely an internal entitlement ledger, never a pre-funded escrow for the payout itself.

Money

Consumer Identity, Checkout & Mobile Apps

One unified phone+OTP identity per Application powers every consumer touchpoint — guest checkout, guest scan, and the Application's own mobile app all resolve to the same account.

Unified consumer identity — no separate sign-up, ever

Verifying an OTP against a phone number is the account: a new number creates one, an existing number logs into it — scoped UNIQUE(application_id, phone). The same account holds order history (ecommerce) and scan/cashback history (scan-and-earn) regardless of which channel first created it. The same phone number on two different Applications is two entirely separate, unrelated accounts.

Ecommerce checkout — a real, payable transaction

1. Phone + OTP at checkoutrequired — there is no fully anonymous order. Doubles as implicit account creation/login
→
2. Addresssaved address book if logged in with history, or a one-off inline address
→
3. Payment via the Application's own gateway sub-accountScan4Earn collects it, but it settles straight to the Application Owner's own bank account — Scan4Earn's and the Tenant's own funds are never in this path (a completely different money flow than the Layer 1/2/3 billing on the previous page)
→
4. Confirmed via signed webhooksame pattern as platform billing — never a client-side callback alone
→
5. Order history & invoicethe same account can log back in later to view orders, track status, and download an invoice

Until an Application's payment sub-account completes onboarding/KYC, its checkout is disabled or COD-only — never allowed to silently fail at payment time.

Scan-and-earn — two scan channels

Channel 1 — Guest/Web scanAny camera/QR scanner → permanent public landing page → phone + OTP (creates/reuses the account for history only) → UPI ID entered fresh, every single time — never read from or saved to any profile → cashback transfers immediately.
Channel 2 — Mobile App scanConsumer registers once inside the Application's own dedicated app (same phone+OTP flow) and adds UPI to their profile once. Logged-in scans resolve identity from the session — no re-entry — cashback auto-transfers to the stored UPI.

Every scan/cashback record is tagged with its channel (guest_web / mobile_app), but both write to the same unified consumer history. A guest-only user who later installs the app and logs in with the same phone number sees their prior scan history already there.

White-labeled mobile apps

A scan-and-earn (or hybrid) Application Owner can commission a fully separate, independently-compiled mobile app — not a shared, runtime-reskinned app — published under their own app-store developer account(s).

Scan4Earn providesa branding-configuration surface (name, icon, splash, colors, bundle ID) and a build pipeline that produces a signed binary per Application on request
One shared codebaseregistration, login, profile, UPI management, scan, history, points/cashback balance, redemption requests — identical across every Application's app. Only the build configuration forks per client, never the code

Real, ongoing cost, accepted deliberately: every shared-codebase update means a rebuild + re-submission per Application, indefinitely — through each app store's normal review cycle (no over-the-air updates in this version). Plan release cadence and support capacity accordingly.

Why the admin tiers stay this thin — root causes in all three layers:
① Database: scans, points_transactions, ecommerce_orders, stock_movements etc. all key on application_id (NOT NULL). No Super Admin or Tenant Admin query is ever written against these tables — the authorization middleware refuses to route to them for those roles, so there is no accidental leak surface.
② Server: Tenant/Super Admin endpoints return only COUNT(*) / SUM(credits_consumed) aggregates from Tenant-grain and Platform-grain tables — they physically cannot return an order row or a scan row because they never join against those tables.
③ Client: the Tenant portal and Super Admin portal ship with zero components that render an order table, a stock number, or a scan chart — those components exist only in the Application-workspace bundle.

Data Model & the Money Loop

One scoping rule makes the whole product enforceable, not just designed correctly: every business fact carries application_id (NOT NULL), and the authorization layer draws a hard line at that grain — Tenant-grain and Platform-grain queries are never allowed to join into it.

GrainTablesRule
Platformfeatures, permissionsGlobal catalogs only. Queryable by Super Admin.
Platform (cont'd)subscription_plansSuper Admin's configurable plan catalog (name, price/month, max Applications) — Layer 1 of billing.
Tenanttenants, tenant_credit_balance, credit_requests, tenant_subscriptions, tenant_credit_rate, product_templates, custom_domainsBilling & provisioning config. Queryable by Super Admin (all rows) and Tenant Admin (own Tenant's rows). Never joined against Application-grain tables in any Super Admin or Tenant Admin query.
Application (tenant_id + application_id, both NOT NULL)products, coupons, coupon_batches, ecommerce_orders, scans, points_transactions, cashback_transactions, stock_movements, webhooks, api_usage_logs, application_subscriptions, application_credit_balance, application_credit_requests, application_credit_transactions, customer_addresses, application_payment_accounts, application_mobile_appsQueryable ONLY by a session whose user_id matches that Application's owner_user_id. No Tenant Admin or Super Admin code path ever selects from these tables. Application deletion = soft-delete — never SET NULL, never CASCADE on financial history.
End userusers (role CUSTOMER), user_upi_detailsOne customer identity per Application: UNIQUE(application_id, phone). user_upi_details rescoped from tenant_id to application_id to match — a real inconsistency found and fixed in this pass. scans/cashback_transactions gain a scan_channel column (guest_web/mobile_app).
Hard architectural rule: no API endpoint that returns rows from an Application-grain table may be reachable by a Super Admin or Tenant Admin session — enforced at the authorization-middleware layer, not just hidden in the UI. The only Application-grain figure a Tenant Admin or Super Admin may ever see is a COUNT(*) or SUM(credits_consumed), and even that is served from a separate, pre-aggregated rollup table — never a live join into orders, scans, or stock_movements.

Removed vs. added in this schema

  • Dropped entirely: dealers, dealer_points, dealer_point_transactions tables.
  • DEALER removed from the users.role CHECK constraint — the only roles left are SUPER_ADMIN, TENANT_ADMIN, APPLICATION_OWNER (collapsed from APP_MANAGER/APP_VIEWER — one login, no viewer tier), and CUSTOMER.
  • Scanning code path simplified: every scan is recorded as a direct consumer scan; no "scanned by dealer on behalf of" attribution exists anywhere.
  • Added for billing: subscription_plans, application_subscriptions, platform_credit_rate, tenant_credit_rate, application_credit_balance, application_credit_requests, application_credit_transactions — the full three-layer model on the Billing page.
  • Added for consumer identity & checkout: customer_addresses, application_payment_accounts (per-Application gateway sub-account/KYC), payment/invoice columns on ecommerce_orders, and application_mobile_apps (white-label build tracking) — see the Consumer page.

Production Rulebook — edge cases a real deployment must handle

Mostly about custom domains and the admin/Application data boundary — because that's where multi-tenant SaaS platforms get burned.

Edge caseRule
Tenant/Super Admin dashboards leaking operational dataTreated as a P0 security bug, not a feature gap. Every dashboard query for these two roles runs against a fixed allow-list of admin-grain tables; any accidental join into an Application-grain table (products, orders, scans, cashback, stock) fails a CI check before it ever ships.
Hostname collisionsGlobal UNIQUE(hostname) — one hostname maps to exactly one target, ever. TXT ownership verification required before activation and re-checked periodically.
Multiple domains per targetAllowed (apex + www + legacy): N rows per target, exactly one is_primary. Non-primary hosts 301-redirect to the primary.
Apex domains can't CNAMEsumukham.com (no subdomain) can't CNAME at most DNS providers. Offer static ingress IPs for A/ALIAS records.
Printed QR codes outlive domainsCritical: coupons are physical — inside paint buckets. QR codes always encode the permanent platform URL (scan4earn.com/s/:code); at scan time the server applies the Application's current branding. Never print a custom domain into a QR.
TLS lifecycleAuto-issue on verification, auto-renew. Renewal failure → status ssl_expiring, alert the Application Owner, grace period.
DNS driftA scheduled job re-resolves CNAME/TXT. Broken → status dns_broken + notification; default *.scan4earn.com URLs are always alive.
Application lifecycleApplication soft-deleted → its domains deactivate (clean 410 page). Re-pointing a domain to a different Application requires fresh verification. Domains NEVER transfer across Tenants.
Ownership handoff can't be reversed casuallyOnce an Application Owner accepts the invite, the Tenant Admin cannot silently reassign ownership — reassignment requires the current owner's consent or a documented support/legal process (e.g. the client business changes hands).
Tenant suspension / non-paymentCustom domains serve a branded "temporarily unavailable" page (not 404). Default admin URLs stay up so the Tenant can pay and recover.
Sessions are per-originA token issued on shop.sumukham.com is capped at that host's scope, and further capped to Meera's own user_id as the Application's owner. Scope = min(role, host) AND identity = registered owner, enforced server-side.
Reserved namespacecustom_domains may never contain scan4earn.com or *.scan4earn.com. Tenant slugs come from a blocklist (www, api, admin, mail, ingress, status…).
Per-host observabilityRate limits and API logs record the hostname alongside Tenant/Application — abuse on shop.sumukham.com is throttled without touching Pals Paint.
EnvironmentsStaging mirrors everything on scan4earn-staging.com with environment-specific verification tokens.
Checkout money never touches Scan4EarnAn Application's checkout must never accept a live payment before its payment-gateway sub-account completes onboarding/KYC (application_payment_accounts.onboarding_status = 'verified') — enforced server-side. Until then: disabled or COD-only, never a silent failure at payment time.
White-label app release overhead is realEvery Application's mobile app is a fully separate, independently compiled and published binary (a deliberate choice, not a default) — a shared-codebase bug fix means a rebuild + full app-store review cycle per Application, indefinitely. No OTA updates in this version. Budget release management accordingly; consider gating this as an opt-in premium add-on rather than a standard offering.
