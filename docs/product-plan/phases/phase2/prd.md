# Phase 2 — Unified Application Dashboard, Feature Flags & Core Operational Screens

**Depends on:** Phase 1 (Application Owner identity must exist)
**Unlocks:** Phase 4 (paywall needs a shell to render inside), Phase 5 (credit-gating needs coupon-batch UI to gate), Phase 7 (analytics needs data these screens produce), Phase 8 (real checkout payments need this catalog/order UI to attach to), Phase 9 (mobile-app scan channel needs this coupon-batch/scan UI to exist first)
**Master reference:** `../../PRD.md`

## Goal

Give every Application Owner one real, working dashboard — not a stub — with the actual operational screens the backend already mostly supports, switched by `app_type` rather than split into separate portals.

## In Scope

### Functional Requirements
- **FR-28, FR-29:** `app_type` (`ECOMMERCE`/`SCAN_AND_EARN`/`HYBRID`), set by the Tenant Admin at provisioning (Phase 1), is the single source of truth for which menu group renders. One dashboard shell/codebase; `HYBRID` sees both groups in the same login, same nav — never a separate URL/subdomain/portal.
- **FR-30 (basic version):** `/api-docs` filters its endpoint catalog by `app_type`. This phase ships the filtered endpoint list; the full Swagger-style try-it-out console, copy-paste code samples, and webhook event catalog are polish items deferred to Phase 7.
- **FR-11b, FR-11c (menu structure only):** Build the Ecommerce menu (Products, Inventory, Orders, Customers) and the Scan & Earn menu (Batches, Coupons, Scans, Redemptions, Cashback) as real, functioning screens. **The "after activation" gating clause is NOT enforced yet** — until Phase 4 ships the paywall, these screens are simply available once the owner logs in. Do not ship this phase to real paying customers without Phase 4 landing alongside it (see Rollout Note).
- **FR-12:** Ecommerce screens: manage product catalog (templates, variants, images, stock), categories, tags; view and transition order status (pending → confirmed → processing → shipped → delivered); view inventory/stock-movement history; manage coupons/discounts scoped to the store; manage API keys and webhooks.
- **FR-13 (CRUD/lifecycle only):** Create coupon batches (reward type, quantity, expiry), generate non-enumerable QR codes, manage draft → printed → active lifecycle, view scan history/cashback/points ledger, approve/reject redemptions. **Credit-balance gating and auto-debit are NOT part of this phase** — batches can be created freely here; Phase 5 adds the enforcement (`application_credit_balance` check + atomic debit). Flag this clearly to stakeholders: this phase alone does not meter usage.
- **FR-14 (UI):** An owner who owns more than one Application gets a switcher between them from one login; each Application's data renders fully independently, never combined.
- **FR-15:** Wire the dashboard entry points referenced by §6.5 of the master PRD — basic KPI numbers and list/table views for both Application types (see FR-21/FR-22 below for exactly what ships now vs. Phase 7).
- **FR-17:** Ecommerce storefront public API (cart, wishlist, checkout) — the Application Owner's own website integrates against this. **Note:** real payment collection, consumer OTP identity, address book, and invoices are NOT part of this phase — checkout here is functionally a placeholder (order gets created, unpaid) until Phase 8 adds the actual payment/identity layer. Do not present this phase's checkout as production-ready on its own.
- **FR-21 (basic slice):** Ecommerce dashboard ships as plain numbers + tables: order count, order list with status filter, low-stock list, unique-customer count. Charts (revenue-over-time, order funnel, top products), CSV export, and webhook-delivery health are Phase 7.
- **FR-22 (basic slice):** Scan-and-earn dashboard ships as plain numbers + tables: total scans, cashback paid, points issued, coupon burn-down percentage, pending redemptions list. Scans-over-time chart, geo heatmap, top-batches table, and failed-payout queue are Phase 7.

### Non-Functional Requirements
- **NFR-4:** Coupon codes generated by the batch-creation flow built in this phase must be non-enumerable/random (not sequential) from day one — this is a correctness bug to avoid introducing, not a later fix.

## Explicitly Out of Scope (deferred)
- Payment/paywall of any kind — Phases 3, 4, 5.
- Credit-balance enforcement on coupon batches — Phase 5.
- Rich charts, heatmaps, CSV export, webhook-health visualization — Phase 7.
- Full self-service API reference (try-it-out console, code samples, webhook catalog) — Phase 7.
- Custom domains — Phase 6.
- Real ecommerce checkout payment, consumer OTP identity, address book, invoices — Phase 8.
- White-labeled mobile app, authenticated (in-app) scan channel — Phase 9.

## Rollout Note

**This phase should not go live for real paying customers on its own.** Without Phase 4's paywall, an Application is fully functional the moment its owner accepts the invite — free of charge, indefinitely. That's fine for an internal beta/demo environment, but Phases 2 and 4 should ship together (or Phase 2 stays behind a flag) before onboarding real Tenants/Applications in production. Similarly, without Phase 5, coupon batches can be created without limit — acceptable for beta, not for a live scan-and-earn Application handling real cashback.

## Definition of Done
- [ ] One dashboard codebase; `app_type` switch verified for all three values, including `HYBRID` showing both menu groups simultaneously.
- [ ] Ecommerce CRUD screens functional end-to-end against the existing backend (catalog, orders, inventory, coupons, API keys, webhooks).
- [ ] Scan-and-earn CRUD screens functional end-to-end (batch creation, QR generation, lifecycle states, scan history, redemption approval).
- [ ] Coupon codes verified non-enumerable (NFR-4) via a randomness/entropy test.
- [ ] Owner with 2+ Applications can switch between them with no data bleed-through.
- [ ] `/api-docs` returns the correct endpoint subset per `app_type`.
